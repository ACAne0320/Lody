# Finite recipient install and signed-report queue

`./keys/host/receive/sqlite` constructs a host-owned recipient workflow in the application's Effect Scope. Trusted composition binds Org, the existing signer/HPKE pair, independently verified ledger supplier, authenticated mailbox transport and one initialization-time native protection capability. It creates no identity, Runtime, task loop, IPC or production assembly. Ordinary `receive` calls never choose a key-store/protector callback.

A new envelope is fixed-authenticated against real current context, and the task preserves original source/context before opening. Real HPKE and commitment verification precede the Install checkpoint. A persisted phase or a pre-existing correct key cannot substitute for verifying this ciphertext: Verify/Install tasks always open the source. The protected store then saves/reloads/unprotects and verifies commitment; a fresh disk key read precedes borrowed signing, fixed signer verification and durable original-report queue. Local publisher installation instead requires the exact genuinely verified genesis/publish record and an already durable key; it does not create a publication/candidate or make a backup decision.

The dedicated 0600 SQLite task file uses APP 0x4c455231/version1, WAL/FULL, fixed Org/recipient and bounded indexed rows. Open rejects old/foreign schema without conversion. Context, ciphertext/publication and signed report originals are retained. Reports retry the first queued bytes without signing again, including after reopen; each retry fixed-verifies context/signature and reloads actual current protected possession. Reported is a local remote-ACK attempt record, not server storage/custody proof or current key availability. A queued claim can retry after its original sender is revoked; a new envelope still requires current eligible sender. Historical envelope eligibility is not loosened.

`receive` returns Installed after actual protected readback and queue preparation, not remote report delivery. Old queued/Reported tasks do not stand in for a lost key. An explicit mailbox repair episode supplies a new revision, so the same retained usable ciphertext can be installed and reported again. An unreadable corrupt protected original stays failed/retained; this layer does not invent a replacement/re-wrapping/recovery-vault procedure.

`resume(limit,cursor)` and `flushReports(limit,cursor)` process one finite indexed keyset page (1–100). Continue their returned `next` hint explicitly; there is no background retry or claim that one call drained all work. A lookahead reads only ID metadata, never another ciphertext. Hints are not transport cursors or across-request snapshots. Blocked revisions are retained rather than trusted as ledger changes. Only a genuine current ledger can end a task as Obsolete/Revoked. Results remain until explicit `acknowledge(id)`; no document/remote cursor is advanced.

Scope closes the databases without erasing tasks/keys. Operations guard closure again after borrowed async work. The caller structures, cancels and awaits its requests plus borrowed signer/ledger/transport before destroying those owners; closing this store does not stop escaped work. Native HPKE/protection retain their established awaited settlement/cleanup brackets. Startup failure requires closure of the consuming Scope.

Tests use actual Ed25519/HPKE, real SQLite, explicit Deferred gates, another process reopening the original report and the actual public mailbox host. The process test uses a declared local RPC bridge, not HTTP/SDK acceptance. The protector is explicitly synthetic. Sender discovery/delivery rounds, durable repair coordination, HTTP/fetch composition, SDK/Lab faults, native adapters, publisher permanent loss and recovery-vault decisions remain separate migration owners. No real keys/keychains or production E2EE are accessed.
