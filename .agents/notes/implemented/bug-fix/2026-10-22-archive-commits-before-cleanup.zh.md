# 归档先提交，再做清理

Status: implemented
Translation: current

[English](2026-10-22-archive-commits-before-cleanup.md)

## 摘要

桌面渲染进程里归档会话时，以前要等一串慢操作完成，行才消失、页面才跳转：先是两次待发输入取消（其中包括等待进行中的 owner 写入结束），然后是对 Repo 里所有脏文档的 flush。现在归档先在本地写入 `isArchived` 就返回。取消改为在后台继续执行，失败会被记录，但不会撤销归档。等它等到进行中的创建结束后，会把那期间晚提交的 Tab 也归档。取消的责任由恢复接手：恢复会在解除归档前先把取消做完，只有做不完时才拒绝恢复。本地提交本身就是乐观更新，所以不需要额外的 UI 覆盖层或回滚状态。

## 为什么调换顺序是安全的

- **held 发送。** `cancelSessions` 在写归档之前就同步中止本窗口的 held 工作，并把它们标记为已取消。held 层在写入前会再检查一次 abort（`session-pending-sends.ts`）。
- **持久化的 Roost 输入。** 每次 owner 写入、lookup 和投递之前，`validateTarget` 都会拒绝已归档的目标，其他窗口的输入也一样。
- **激活。** `activateUserTurn` 会跳过已归档会话；CLI 的 dispatch watcher 遇到已归档的 meta 时不做任何事（`session-dispatch-logic.ts`）。
- **剩余情况。** 已经越过最后一次 abort 检查的写入仍可能提交，这和旧的“先等待再写入”顺序完全相同。变的只是它与归档标记的先后，而已归档会话永远不会启动工作。
- **晚到的 Tab。** 旧顺序在等待结束后才扫描目标，所以等待期间提交创建的 Tab 会被一起归档。现在由后台步骤恢复同样的结果：等待结束后用同一种操作重新读取目标（`archive`，或用户选择连同打开的会话一起归档时的 `archive-tree`），把首次扫描里没有的 Tab 也归档。前提是根会话仍处于归档状态，这样中途被恢复的会话不会被重新归档。

只有在新会话的元数据还没写入时，归档才会等它的取消完成，因为这时有没有东西可归档取决于进行中的写入。元数据一旦存在，它的首次 owner 写入（最长到 30 秒的 RPC 超时）就只是普通的后台步骤，归档不再等它。

## 清理责任

后台步骤失败后，已持久化的输入没有被打上 `canceled` 标记。本窗口仍会跳过它，因为内存里的 `canceled` 集合记着它；但重载之后，或者在其他窗口里，一旦会话不再处于归档状态，`resume` 就会把它投递出去。所以能让遗留输入重新变得可投递的，只有“解除归档”这一步。

`restoreSession` 在清除 `isArchived` 之前，会对恢复目标执行 `cancelSessions`。如果存储仍然故障，恢复会带着原始错误被拒绝，状态不变；存储恢复后，下一次恢复就能成功。这个闸门只作用于恢复，归档、发送和无关会话都不会等它。正常路径下它只多一次输入存储读取，因为成功完成的归档不会留下要取消的东西。工作区关闭导致后台步骤中止时，只按 `info` 级别记录，错误报告里不会把它当成失败。

## 验证

`tests/use-session-actions.test.ts` 用真实的 held 发送队列覆盖了：

- 某个上传忽略 abort、仍在被等待时，归档已经返回；
- 扫描之后才提交创建的 Tab 会被后台步骤归档；
- 元数据已存在的新会话，在首次写入被挡住时仍能完成归档，之后落地的那条消息不会被激活；
- `flush` 卡住、取消也失败时，归档仍然生效；取消持续失败期间恢复会被拒绝，会话保持归档状态；故障解除后，恢复会先丢弃遗留的输入，再解除归档。

去掉任何一处对应的改动，相应的新断言都会失败。未验证：在真实的流式工作区里用 Electron 实测延迟。
