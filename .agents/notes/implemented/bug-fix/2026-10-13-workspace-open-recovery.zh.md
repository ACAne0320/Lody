# 恢复一直打不开的工作区

Status: implemented
Translation: current

[English](2026-10-13-workspace-open-recovery.md)

## 摘要

有些用户每次打开 Lody 都停在“正在切换工作区”，直到重装才恢复。原因是工作区的本地副本损坏，导致
runtime 创建或它的首次元数据扫描被拒绝，而这两者都没有任何重试。唯一有效的办法是“设置 → 清除本地缓存”，
但在这个界面里根本进不去。现在占位页把这两种失败认定为终态：遇到其中任意一种，它会清除一次本地缓存并
重新加载，这一步交给现有的启动时清除来安全完成。如果清除后仍然失败，或者只是等待时间过长，页面上会直接
提供清除缓存、重新加载、复制诊断信息和完全重置。自动清除每 24 小时最多一次，并且只在联网时执行。扫描如果
是一直挂起而不是失败，只会出现手动页面，不会自动清除。这一点尚未在真实卡住的用户上验证。

## 问题

`resolveWorkspaceDataScope` 会让内容区停在“正在切换工作区”占位页，直到 runtime、路由和 doc-metadata
的归属一致。[卡住同步遥测](../feature/2026-09-26-workspace-sync-stuck-telemetry.zh.md) 已经能说出是哪个
条件卡住了，但它刻意没有改变任何行为。有两条路径是死路，而且重启也无法恢复，因为造成它们的状态保存在
Chromium 存储里：

- **首次 doc-metadata 扫描被拒绝**（`doc_meta_scan_failed`）。仓库 IndexedDB 损坏、超出配额或连接正在
  关闭时会发生。scope 会保留 `scanFailure`，而在 runtime 被替换之前没有任何东西会重新扫描。
- **创建 runtime 被拒绝。** `LoroRepo.create` 在任何内容渲染之前就会打开并读取仓库 IndexedDB。
  `RuntimeProvider` 此前只是记录错误，把 runtime 设为 null、控制连接设为 `error`。scope 于是显示为
  `runtime_missing`，看起来和普通的等待一模一样。

清除缓存恰好会移除这些被污染的状态：所有 `lody*` 数据库、slug→id 映射、Streams 令牌以及游标绕过标记。
但用户只能在设置里或通过 CLI 找到它，于是重装就成了最直观的修复方式。

## 决定

- **让 runtime 创建失败可见。** runtime 创建被拒绝时，`RuntimeProvider` 会记录
  `workspaceRuntimeInitFailureAtom`（`{ workspaceSlug, errorType }`），并在每次新的尝试开始时清空。
  当失败属于目标 slug 时，scope 报告 `runtime_init_failed`，卡住同步上报因此能把它和普通等待区分开。
  与扫描失败一样，这里只保留错误名称。`describeErrorType` 会从任意对象上读取 `name`，因为并不是每个
  引擎里的 `DOMException` 都是 `Error`。
- **终态时只自动清除一次缓存。** 遇到 `runtime_init_failed` 或 `doc_meta_scan_failed` 时，占位页调用
  `armAutomaticCacheClear` 并重新加载。这个函数设置的是现有的启动标记，所以删除仍然发生在启动阶段，在
  runtime 重新打开这些数据库之前。以下情况它会拒绝：
  - 在隐藏的预热窗口中，因为它的启动流程不会消费这个标记；
  - 距离上次自动清除不到 24 小时，包括系统时钟回拨的情况；
  - `lody:automaticCacheClearAt` 标记无法写入或读回时。

  这个标记刻意不在清除缓存的删除列表里，所以它能在自己所记录的那次清除之后保留下来。没有它的话，一次
  无效的清除会导致无限重新加载。

- **离线时从不自动清除。** 清除会删除所有工作区的离线副本，而离线时这些副本都无法重新下载。手动操作仍然
  会显示。
- **出路就放在占位页上。** 终态下的自动清除被拒绝后，或者任何等待超过 20 秒后，占位页会变成一个状态页，
  提供：
  - “清除本地缓存并重试”，使用与设置页相同的确认对话框；
  - “重新加载 Lody”；
  - “复制诊断信息”和技术详情区：卡住条件、错误名称、工作区、等待时长、连接状态、上次自动清除时间、
    构建信息以及会话渲染轨迹；
  - 现有的完全重置对话框，以一个低调的脚注链接呈现。

  `$workspaceName/_auth.tsx` 中已登录的内容区占位页和无本地令牌时的启动占位页都使用它。

- **挂起只显示，不清除。** 一直不结束的扫描或 runtime 只会得到手动页面。另一个窗口占用着数据库时，清除
  无法解除阻塞；而在大工作区、慢设备上，慢并不等于坏了。

## 未采用的方案

- **原地重试扫描或 runtime。** 这没有用：走到这里的失败要么是持久化的损坏，要么是一个重新加载也修不好的
  正在关闭的连接。它还会带来遥测笔记中警告过的重试风暴。
- **扫描超时后自动清除。** issue 里提出了这个方案。它会在慢设备上清掉健康的缓存，而且被阻塞的打开操作
  本来就清除不了。20 秒后的手动入口已经覆盖了这种情况。
- **等待存储危机熔断（#438）。** 那个 PR 会识别配额耗尽和连接失效，并要求重启应用。它仍未合并，也不覆盖
  数据损坏或扫描失败。本改动不依赖它。它合并后，它的危机界面负责它自己识别的失败，并显示在这个占位页之上。

## 已排查的原因：仓库存储升级

受影响的 iOS 用户都是很久没打开应用后遇到卡死，这与一次跨越多个 loro-repo 存储变更相符。
最后一次打开早于 0.20.3（2026-09-27）的用户，仓库数据库仍是 schema v3，下次启动时会执行
v3→v4 的 IndexedDB 升级。

在 fake-indexeddb 下的实验排除了这一点：

- **写入：** 每个发布过的版本（0.19.1、0.20.0、0.20.3、0.21.0–0.21.2、0.22.0）搭配当时的
  `loro-crdt` 和 Flock 版本，写入带多次修改和删除的会话与机器元数据，以及一个文档和一个 Flock
  文档。其中一部分数据库正常关闭，另一部分不经过仓库关闭流程。
- **读取：** 0.22.0 用 runtime 的参数打开每个数据库，并运行真实的 `docMetaSubscriptionAtom` 扫描。
- **结果：** 所有数据库都升级到 v4，scope 就绪，会话、删除、文档和 Flock 的值都符合预期，第二次
  启动仍可读取。0.19.1 写入的 3000 个会话约 0.6 秒完成打开和扫描。
- **反向对照：** 损坏元数据快照后，`LoroRepo.create` 抛出 `Failed to hydrate metadata snapshot`。
  这表现为 `runtime_init_failed`，而不是扫描挂起，说明这套实验能发现不兼容。

局限：WebKit 的 IndexedDB 不同于 fake-indexeddb；只测了本地写入的元数据，没有测从 Streams 导入的
元数据。

本地 schema 不兼容也会被清除缓存移除，而用户反馈清缓存无效。仍未排除的有两种原因：

- WebKit 上 v3→v4 升级本身失败；
- 能在清缓存后保留的状态。`useOrganization` 在五次尝试后不再重试工作区列表，而清缓存会删除
  slug→id 映射缓存，应用正是靠这份缓存才能在没有列表时启动。

## 验证

- `tests/workspace-open-placeholder.test.tsx`：
  - 扫描失败或 runtime 创建失败时会设置清除标记、重新加载，并上报 `workspace/auto_cache_clear`；
  - 冷却期内的第二次失败显示手动页面，不设置任何标记；
  - 离线时不设置标记；
  - 挂起的扫描恰好在延迟到达时变成慢速页面，而不会清除；
  - 诊断信息包含卡住条件、错误以及上次自动清除时间。
- `tests/clear-local-cache.test.ts`：冷却期、标记在启动清除后仍然保留、时钟回拨，以及无法写入标记的情况。
- `tests/runtime-provider.test.tsx`：创建被拒绝会被记录，并由下一次尝试清空。
  `tests/workspace-data-scope.test.ts`：`runtime_init_failed` 只作用于目标 slug。
- 未验证：Electron 中真实被污染或配额耗尽的用户配置。在生产环境中，`workspace/sync_stuck` 按卡住条件的
  统计和 `workspace/auto_cache_clear` 事件会说明一次自动清除是否足够。
- 已知限制：正在关闭的 IndexedDB 连接绑定在渲染进程上，重新加载未必能修复，而这里不会重启应用。这样的
  用户仍会落到手动页面并需要重启，这正是 #438 要说明的情况。
- 后续：为 `workspace_not_in_organizations` 提供按卡住条件的出路，以及 #417 的第二阶段。
