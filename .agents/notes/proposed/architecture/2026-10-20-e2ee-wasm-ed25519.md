# WebAssembly strict Ed25519 for E2EE ledger verification

Status: proposed
Translation: current

[中文](2026-10-20-e2ee-wasm-ed25519.zh.md)

PRs: this change (stacked on [LodyAI/Lody#1733](https://github.com/LodyAI/Lody/pull/1733))

## Abstract

Ledger replay was slow because of pure-JS elliptic-curve arithmetic, not because of the protocol. Core now verifies Ed25519 with a small Rust module compiled to WebAssembly. The module applies exactly the existing strict rules, and full replay gets 7–13× faster. A differential test shows the module accepts the same keys and signatures as the pure-JS path, including on adversarial inputs. When WebAssembly is unavailable, core falls back to pure JS with identical results. In a local Convex deployment the module runs in queries, mutations and actions.

## Problem and evidence

Profiling full replay put about 70% of the time in noble's curve arithmetic. Every signature runs these strict steps (per-call times on an 8-core 2.2 GHz Xeon under load):

| Step | Pure JS |
|---|---|
| noble `verify` (zip215: false) | 3.4 ms |
| prime-subgroup check of R (`isTorsionFree`) | 1.9 ms |
| subgroup check of A (cached for only 256 keys) | 1.9 ms |
| Web Crypto verify (replaces only the first row) | 0.36 ms |

The subgroup checks are required. Ed25519 implementations disagree on points with a small-order component, and every client and host must reach the same verdict on every record. Web Crypto therefore halved the cost at most.

## Approach

- **Crate.** `packages/e2ee-core/wasm/ed25519-strict` uses curve25519-dalek 4.1.3 and sha2.
  - A and R must be canonical, nonzero and in the prime-order subgroup, A must not be of small order, S < L, and the cofactored equation must hold. These are the same rules noble applies with `zip215: false` plus core's subgroup checks.
  - All inputs are public, so the module uses variable-time multiplication; `[L]P` is computed as `[L−1]P + P`.
  - It uses the 32-bit field backend, which measured faster than the 64-bit one in WebAssembly.
- **No glue code.** There is no wasm-bindgen. Raw exports (`input`, `key_ok`, `verify`) work with plain `WebAssembly.Instance`. The module is 74 KB, embedded in core as base64 with its SHA-256.
- **Fixed backend, not injectable.** `foundation/ed25519-wasm.ts` instantiates the module synchronously on first use. If WebAssembly is absent or refuses, every call returns `undefined` and core uses the pure-JS path. `signingPublicKey` and both verify entry points try the module first.
- **Pre-checked keys.** `verifySignature` has always validated A through `signingPublicKey`, which caches the result. It now tells the module so, and the module skips A's subgroup check; A is still decoded canonically.
- **Reproducible build.** `node wasm/ed25519-strict/build.mjs` runs `cargo build --locked` and regenerates `ed25519-wasm.generated.ts`. Two rebuilds produced the same hash. CI does not build Rust; a test checks that the embedded bytes match the recorded hash.
- **Licenses.** The compiled crates are listed in `THIRD_PARTY_NOTICES.md`, with their license texts under `wasm/ed25519-strict/licenses/`.

## Evidence

Differential test (`test/ed25519-wasm.test.ts`):
- **Inputs:**
  - 50 valid keys and 500 random keys;
  - all eight small-order points;
  - mixed-order keys;
  - every non-canonical encoding;
  - valid, tampered and S+L signatures;
  - signatures whose R has a torsion component and that satisfy the cofactored equation (asserted to pass noble's raw `verify`);
  - messages from 0 to 20,000 bytes.
- **Result:** module and pure-JS reference agree on every input, and core returns the same results and error codes with and without WebAssembly.
- **Mutation checks:**
  - removing R's subgroup check fails the test;
  - removing the canonical-encoding check cannot be caught by any input, because no prime-order point has a non-canonical encoding; the test asserts that fact.

Core suite: 411/411 with WebAssembly as the default. The Web Crypto fallback tests turn it off.

Performance with real keys and signatures, full replay, same host and load:

| Ledger | Records | Pure JS | WebAssembly | Speedup |
|---|---|---|---|---|
| 4,096 rotations | 4,097 | 27.1 s | 4.0 s | 6.8× |
| 1k members + 1k devices + 2k rotations | 4,001 | 43.2 s | 5.6 s | 7.7× |
| 4k members + 4k devices | 8,001 | 156.9 s | 12.4 s | 12.7× |

- **Per signature:** 0.42 ms in WebAssembly vs 0.15 ms natively in Rust.
- **Rest of replay:** what remains is mostly JS: CBOR decoding, hashing and generators.

Convex: a probe deployed to a local Convex backend (in a container, with raised local time limits) instantiated the module in a query, a mutation and an action. It accepted a valid signature and rejected a tampered one in each. The action measured 0.65 ms per verification.

## Limits

- **Platforms without WebAssembly** (for example React Native's Hermes) keep the pure-JS speed.
- **Browser main threads:** a synchronous compile there may be refused for large modules. This 74 KB module is within the usual limits, and any refusal falls back to pure JS.
- **Measured hosts:** speed was measured on one loaded host and in a local Convex backend, not on production Convex or on devices.

## Alternatives considered

- **Web Crypto only:** about 2×, because the subgroup checks stay in JS.
- **Native N-API addon:** about 40×, but needs per-platform binaries and is unavailable in Convex's default runtime and in browsers.
- **Dropping the subgroup checks:** rejected. It would change which ledgers verify and break agreement between implementations.
